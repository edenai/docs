The **Management API** lets your automation create and manage inference keys **programmatically**: the
capability you had with a long-lived account key, restored without the security downside of a single
permanent credential that can call inference directly.

## The three tiers

The chain separates the durable credential you store from the key that actually spends:

| Tier | Prefix | What it can do | Where it comes from |
|------|--------|----------------|---------------------|
| **Issuer key** | `mgmt-eden-…` | Mint **auth keys**, nothing else. It cannot read, write, or call inference. | Generated once from the dashboard (**Account → Management Keys**). |
| **Auth key** | `mgmt-eden-…` | Manage the org (`manage:read` / `manage:write`), including minting **inference keys**. | Minted by an issuer key, or from the dashboard. |
| **Inference key** | `sk-eden-…` | Call the inference API (bills the org). | Minted by an auth key with `manage:write`. |

Because the issuer key can only *mint*, a leaked issuer key is contained by auditing and revocation at
every hop, but it can still mint its way down to inference, so **store it like a root secret**.

## Quickstart

<Steps>
<Step title="Generate an issuer key">
From the dashboard (**Account → Management Keys**), generate an **issuer key**. Copy it once; it is shown
only at creation. The org owner can always do this; the owner can also grant the *API Key Management*
permission to other members via roles.
</Step>
<Step title="Mint an auth (worker) key">
{/* skip-test: reads $ISSUER_KEY, which the reader exports in the step above */}
```bash
curl -X POST https://api.edenai.run/v3/manage/auth-keys \
  -H "Authorization: Bearer $ISSUER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "ci-worker", "scopes": ["manage:read", "manage:write"]}'
```
Returns a `mgmt-eden-…` auth key (shown once). An issuer key can never mint another issuer key.
</Step>
<Step title="Mint an inference key">
{/* skip-test: reads $AUTH_KEY, which the step above prints for the reader to export */}
```bash
curl -X POST https://api.edenai.run/v3/manage/keys \
  -H "Authorization: Bearer $AUTH_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "prod", "balance": "25", "balance_reset_period": "monthly", "balance_reset_amount": "25"}'
```
Returns an `sk-eden-…` inference key (shown once) with the budget/expiry you set. Use it exactly like any
Eden AI inference key.
</Step>
</Steps>

## Keys are permanent by default

Management and inference keys do **not** expire unless you set `expire_time` explicitly. Regeneration is
deliberate: to roll a worker key, mint a fresh one with your issuer key and revoke the old one. The
durable issuer key is always available to do this without a human in the loop.

## Endpoints

All endpoints authenticate with `Authorization: Bearer <mgmt-eden key>` and are scoped to the calling
key's organization. The one exception is `/v3/manage/routing-policies`, which also accepts a member's own
inference key (`sk-eden-…`) and then manages that member's personal policies.

| Method & path | Scope | Purpose |
|---------------|-------|---------|
| `POST /v3/manage/auth-keys` | `manage:mint` | Issuer mints a worker key |
| `GET /v3/manage/auth-keys` | `manage:mint` | List the org's management keys |
| `DELETE /v3/manage/auth-keys/{key_id}` | `manage:mint` | Revoke a worker key |
| `GET · POST /v3/manage/keys` | `manage:read` · `manage:write` | List / mint inference keys |
| `GET · PATCH · DELETE /v3/manage/keys/{key_id}` | `manage:read` · `manage:write` | Read / update / revoke an inference key |
| `POST /v3/manage/keys/{key_id}/rotate` | `manage:write` | Rotate an inference key's secret |
| `GET /v3/manage/members` · `/usage` · `/keys/{key_id}/usage` · `/whoami` | `manage:read` | Members, usage, key introspection |
| `PATCH /v3/manage/members/{email}/role` | `manage:write` | Set a member's role |
| `GET /v3/manage/groups` | `manage:read` | List the organization's directory-synced groups |
| `GET /v3/manage/groups/{external_group_id}` | `manage:read` | Retrieve one group and its members |
| `GET /v3/manage/routing-policies` | `manage:read`, or an inference key | List the routing policies the credential can use: the organization's with a management key, the member's own and the organization's with an inference key |
| `GET · PUT · DELETE /v3/manage/routing-policies/{name}` | `manage:read` · `manage:write`, or an inference key | Read / create or replace / delete a routing policy: the organization's with a management key, the member's personal one with an inference key |

### Members and roles

`PATCH /v3/manage/members/{email}/role` assigns a role to a member by email and returns the updated
member. The request body is `{"role_id": <id>}`. The outcomes:

| Status | Cause |
|--------|-------|
| `200` | The role is assigned and the updated member is returned |
| `400` | `role_id` is missing or not an integer |
| `403` | The member is the organization owner, whose role cannot be changed |
| `403` | The role grants more than member management and read access. A `manage:write` key may assign only roles limited to those two permissions, so a role holding API Key Management, organization configuration or billing authority is refused |
| `404` | The email is not an active member of the organization, or `role_id` names no role available to the organization (unknown, or belonging to another organization) |
| `409` | Role-based access control is not enabled for the organization |

### Groups

Groups are `DirectorySyncGroup` records synced from your identity provider over SCIM. They are
read-only here: they are created and maintained in the identity provider, never through this API.
`external_group_id` is the group's id in that provider and is what the detail URL takes. Each group
returns the emails of its active members, matching `/v3/manage/members`, so the two can be
correlated. A group belonging to another organization returns `404`.

## Routing policies

A [routing policy](/v3/llms/routing-policies) is a saved model chain and its provider preferences, called from an inference request as `model: "policy/{name}"` or applied to every chat call of an inference key through the key's `default_policy` field (on `POST` and `PATCH /v3/manage/keys`). With a management key these endpoints manage the organization's policies; called with a member's own inference key, they manage that member's personal ones.

## Migrating from a dashboard-only key

If your pipeline previously created keys through the dashboard-only flow, move it to this API: generate an
issuer key once, then have your automation mint auth and inference keys as above. Inference keys minted
here behave identically to keys created in the dashboard.
